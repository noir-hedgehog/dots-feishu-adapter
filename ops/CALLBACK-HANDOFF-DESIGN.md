# Callback handoff proposal (not activated)

Confirmed live failure: subscribe HTTP400 / RPC-32015 / local_approval_pending; challenge_attempts0. No evidence that the latest callback reached challenge verification.

Approval persistence: Control.update uses BEGIN IMMEDIATE, encrypts the whole control state and commits SQLite before returning. Runtime and CLI open the same configured control_path. callback_approved is not cleared at normal startup; explicit revoke clears it. Avalon nonsecret configuration points at the expected private regular control.sqlite3 file. Offline reopen test retains the approved digest. Live approved/pending digest counts remain unverified because their state is encrypted and agent access to production secrets is excluded. A human-run metadata helper exists; do not execute it as the agent.

Recommended candidate: retain one original authenticated events/subscribe request while an already-open local CLI waits for its exact candidate. The CLI displays the complete exact destination only on the user's terminal, requests explicit ACCEPT CALLBACK, and commits the same existing approval. Server notices approval, rechecks the exact owner/chat binding and audience, revalidates public DNS/TLS policy, signs a fresh challenge using the original in-flight secret, requires2xx and echo, then returns success to the ORIGINAL JSON-RPC request. No new CREATE, no callback substitution, no domain allowance, no background application delivery before success. No secret is persisted for the pending handoff. Only one pending in-flight request should be admitted; a new request must not inherit an abandoned request's waiting state.

The wait is opt-in, bounded (candidate15s), and defaults off. User must have the local confirmation terminal ready before the single platform CREATE. Timeout/revocation results in the same rejected request, no challenge and no saved subscription; it does not automatically trigger another CREATE. User may approve too late, so CLI must also confirm that the original request is still waiting before accepting a handoff. Request cancellation must be propagated or otherwise detectably handled before challenge; current WSGI interface does not expose a reliable disconnect signal. Do not claim a cancellation guarantee from a fake test.

Remaining platform constraint: public tunnel-client v0.0.15 docs describe an effective connection window bounded by MCP_CONNECTION_MAX_TTL(default10m), but do not establish the TaskService CREATE / events-subscribe deadline. poll_timeout(default30s) is empty-poll waiting, not an RPC budget. Need product-supported deadline/cancellation information, or an explicitly authorized single bounded timing experiment, before activating this candidate. SSE transport may carry progress, but it does not itself prove TaskService waits longer or supports resuming a failed CREATE. No public documented callback-preserving failed-CREATE resume mechanism has been found.

Offline tests prove same-request success after precise approval, timeout/revocation fail closed, and SQLite approval persistence. They do not prove TaskService timing compatibility or live approval contents.
